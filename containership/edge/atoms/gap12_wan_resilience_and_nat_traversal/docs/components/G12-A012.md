# G12-A012 — NAT64 / DNS64 compatibility (P1)

_Generated from `evidence/registry.py`; lifecycle **implementation**._

## Normative requirement
- **Success:** Pref64::/n derived per RFC 7050/6052 and synthesized candidates kept apart from native ones.
- **Failure:** any other outcome, reported with a registered reason code (`wan/reasons.py`); failures never silently fall back to a less-trusted path.
- **Degraded:** a dependency is down/stale (see `wan.state.degraded_policy`); existing trusted sessions continue until trust expiry, new ones are refused.
- **Unsupported:** live DNS64 query of ipv4only.arpa (answers are an input); DNSSEC interaction — reported as `UNSUPPORTED` / NOT-EVIDENCED, never emulated.
- **Policy rejection:** `POLICY_*` reason codes (egress, mechanism disabled, quarantine, untrusted peer, config rejected).

## Interfaces
- `wan.natclass.discover_nat64_prefixes`
- `wan.natclass.synthesize`
- `wan.natclass.is_synthesized`

## Dependencies and trust boundaries
- DNS64 resolver

- none

- See the module docstring of the interfaces above for the RFC/specification sections implemented and the explicit deviations.

## Operator diagnostics
- empty prefix list = no NAT64 detected
- Escalate (do not auto-retry) on AUTH_* reasons, DNS_MISMATCH, audit-chain breaks and quota exhaustion.
- Disable: kill-switch control naming the mechanism (`wan.rollout.KillSwitch`), or `mechanisms.<name>=false` in config.
