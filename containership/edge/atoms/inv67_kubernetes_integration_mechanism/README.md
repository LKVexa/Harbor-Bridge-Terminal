# INV-67 — Kubernetes integration mechanism

**Version:** 4.3.0  
**Group:** 01_Source_Inventory  
**Series:** Post-Kubernetes Master Prompt & Workflow Series v4.0.0  
**Checklist:** 100 requirements across ten dimensions in `CHECKLIST.json`

INV-67 is a strict Kubernetes Pod-subset translation boundary for migration into the target runtime, and — from v4.3.0 — a Kubernetes-native integration plane around it: a `WasmWorkload` CRD, a leader-elected reconciler, a fenced/idempotent downstream adapter, and the security, resilience, observability and release machinery required by `docs/governance/INV67_v4.2.0_MISSING_COMPONENT_IMPLEMENTATION_CHECKLIST.md`. The reference implementation converts a deliberately small, documented subset of a Kubernetes `Pod` into a placement request. Semantics outside that subset are rejected with machine-readable field paths rather than silently discarded.

## Responsibility

Own the Kubernetes bridge: Pod-subset translation, explicit refusal of unsupported fields, label/annotation/resource mapping, and status projection back into Kubernetes Pod phases.

## Supported translation subset

The v4.2.0 reference translator accepts:

- top-level `apiVersion: v1`, `kind: Pod`, `metadata`, and `spec`;
- `metadata.name`, `metadata.namespace`, `metadata.labels`, and `metadata.annotations`;
- a non-empty `spec.containers` array;
- for each container: `name`, `image`, and `resources`;
- `resources.requests` and `resources.limits` containing `cpu` and/or `memory` quantities;
- an empty `securityContext` as a no-op.

The translator explicitly refuses unsupported Kubernetes semantics, including unknown Pod/spec/container/resource fields, init containers, volumes, host networking, host PID namespace use, and non-empty container security contexts. Privileged containers and `hostPath` mounts receive specific refusal reasons.

## Output contracts

- `PK_K8S_TRANSLATE/1` — translated placement request (`schemas/PK_K8S_TRANSLATE_v1.schema.json`)
- `PK_K8S_REFUSE/1` — structured refusal/validation error (`schemas/PK_K8S_REFUSE_v1.schema.json`)
- `PK_K8S_STATUS/1` — runtime state projected to a Kubernetes Pod phase (`schemas/PK_K8S_STATUS_v1.schema.json`)

The `cpu` and `memory` fields on each translated unit remain as backward-compatible aliases for resource **requests**. Canonical v4.2 output also contains explicit `requests` and `limits` objects.

## Owns

- Pod-subset translation
- Explicit refusal of unsupported fields
- Label and annotation mapping
- Resource request and limit mapping
- Status projection back to Kubernetes

## Explicitly does not own

- Kubernetes API server behavior
- Runtime placement decisions (SCH-01 / INV-68)
- Image building
- Cluster networking

(v4.3.0 note: the earlier non-goal "Kubernetes operators/controllers" is superseded by ADR-001 — INV-67 now owns the `WasmWorkload` controller, and only that one.)

## Non-goals

- Running an API server
- Deciding placement
- Building images

## Service-level objectives

- **No silent drops:** every requested semantic outside the supported subset is refused by field path.
- **Fidelity:** supported requests and limits are normalized without intentionally dropping values.
- **Translation time:** declared target p99 under 5 ms; a reproducible benchmark gate is still a production gap (see `AUDIT_REPORT.md`).

## Local verification

The pure translator has no `pk_core` dependency and can be tested standalone:

```text
python tests/test_translation.py
python -O tests/test_translation.py
python -m unittest discover -s tests -t tests -p 'test_*.py'   # full v4.3 suite
```

The checklist/conformance harness requires the sibling `pk_core` package:

```text
python tests/test_component.py
```

When `pk_core` is not importable, `test_component.py` intentionally skips its three integration checks. That skipped state is **not** production acceptance evidence.
